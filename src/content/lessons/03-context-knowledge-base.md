## 為什麼需要

把所有 PDF、筆記、舊稿與聊天紀錄一次塞給 AI，不等於提供完整背景。過量 Context 會讓重要限制被淹沒；過期版本與無來源摘要更可能互相衝突。研究知識庫的價值不是「資料越多越好」，而是知道每項資訊從哪裡來、目前是否有效、什麼任務才需要載入。

可維護的工作區應把原始來源與衍生內容分開。原始來源是核對依據；索引與摘要是導航層；任務封包只放本次決策必要的材料。

## 任務

從一個包含論文、筆記、資料說明與草稿的研究資料夾，建立三層結構：

1. **來源層**：原始 PDF、資料字典、實驗紀錄與正式規範，不改寫。
2. **索引層**：檔案清單、書目資訊、關鍵主題、抽取狀態、版本與來源位置。
3. **任務層**：為一個明確任務組成精簡 Context 封包，列出必讀、選讀與禁止使用的資料。

## 做法

先建立來源清單，每筆至少包含：

```text
id：穩定且不隨檔名小改而變動的識別
title：人能辨識的名稱
path_or_url：原始位置
source_type：論文／資料／規範／研究筆記／草稿
version_or_date：版本或取得日期
authority：正式來源／作者手稿／內部筆記／未驗證摘要
sensitivity：公開／內部／敏感
extraction_status：未處理／已抽取／需人工看圖表
```

再建立短摘要，但每段摘要都保留來源 ID 與定位。摘要應回答「這份資料能用來做什麼」，不要假裝取代原文。

最後為單一任務製作 Context 封包：

```text
任務問題：
必讀來源與理由：
可選來源與使用條件：
不可使用的舊版或未驗證內容：
本任務採用的術語與定義：
已知衝突：
回答時必須保留的引用格式：
```

定期更新時，優先更新索引與狀態，不直接覆寫原始來源。若新版取代舊版，保留關係與原因。

## 工具配方

### 網頁 AI：設計分類，不放入敏感原文

提供匿名化的檔案類型與研究目標，請 AI 建議索引欄位、命名規則與遺漏檢查。真正的資料路徑、內容與權限仍由研究者管理。

### NotebookLM：建立有界的主題來源集

以研究問題或章節建立 notebook，不必把整個研究生涯放進同一個來源集。加入來源後先問：「目前來源涵蓋哪些主題？有哪些問題無法由這些來源回答？」使用引用跳回原文，並記錄加入與移除日期。

### 檔案型 Agent：產生索引與任務封包

```text
請只讀取指定資料夾，建立檔案清單與建議分類。
不要搬動、改名或刪除原始檔。
無法可靠抽取的公式、表格與掃描頁請標記，不要猜內容。
輸出需保留原始路徑與更新時間。
```

### CLI：做可重跑的機械處理

大量檔案可用既有工具抽取文字、計算檔案雜湊或搜尋關鍵詞。先在副本或輸出目錄測試，保存指令、版本與失敗清單；不要用臨時腳本悄悄改動來源檔。

## 人工檢查點

- 權威來源與個人筆記是否明確分級。
- PDF 抽取後的公式、上下標、表格與欄位是否失真。
- 索引中的日期是出版日、取得日、資料收集日還是最後修改日。
- 敏感資料是否被錯誤放入可上傳或可共享的來源集。
- 任務封包是否排除已知舊版、撤回資料與不相容定義。

## 常見失敗

- **把聊天摘要當權威來源**：摘要只能當導航，核心主張仍需回原文。
- **一個超大 notebook 解決所有問題**：來源邊界不清，回答難以判斷適用範圍。
- **只做檔名清單**：缺少版本、權威性與敏感等級，無法安全使用。
- **索引沒有更新策略**：新舊版本並存，AI 隨機引用。
- **抽取成功等於內容正確**：掃描、雙欄、公式與圖表常需人工檢查。

## 驗收清單

- [ ] 原始來源與衍生摘要存放位置不同。
- [ ] 每筆索引都有穩定 ID、來源位置、版本與權威性。
- [ ] 敏感等級與可分享範圍已標示。
- [ ] 抽取失敗或需人工看圖表的檔案有清單。
- [ ] 任務封包只包含本次問題需要的材料。
- [ ] 已知定義衝突與舊版排除規則已寫明。
- [ ] 任何摘要都能回到原始來源核對。

## 延伸挑戰

為同一批資料建立兩個不同任務的 Context 封包，例如「撰寫方法章」與「回覆審稿意見」。比較哪些來源是共同必讀、哪些只應出現在單一任務，並說明過量 Context 可能造成的誤判。
