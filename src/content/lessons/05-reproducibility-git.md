## 為什麼需要

可重現不是「我電腦上曾經跑成功」，而是另一個人能知道使用哪份程式、資料、參數與環境，並理解預期產物。Git 能追蹤文字型檔案的變化與研究決策，但它不會自動保存大型資料、執行環境、外部服務或未記錄的手動步驟。

AI 讓修改速度變快，也增加一次改動過多、覆蓋使用者工作或聲稱驗證完成的風險。版本控制的重點不是頻繁備份，而是讓每個改動都有範圍、理由與驗證證據。

## 任務

為一個小型研究分析建立可重現版本：

- 保存原始碼、設定、環境說明與執行入口。
- 記錄資料來源、取得日期、版本或雜湊；不必把敏感或大型資料放進 Git。
- 從乾淨起點重跑一次核心結果。
- 用至少兩個有意義的 commit 分開「分析改動」與「文件或圖表改動」。
- 寫下預期輸出與已知差異來源。

## 做法

1. **盤點追蹤範圍**：程式、設定、文件與小型測試資料通常適合進 Git；憑證、個資、生成快取與大型資料通常不適合。
2. **建立乾淨起點**：在 AI 動手前確認尚未保存的修改，避免把他人工作混進同一批次。
3. **記錄環境**：保存依賴版本、系統需求、隨機種子與外部工具；依專案語言採用現有鎖定機制。
4. **固定執行入口**：用 README、任務腳本或 notebook 說明從輸入到產物的順序。
5. **小步修改與檢查差異**：每個 commit 回答「改了什麼、為何改、如何驗證」。
6. **從乾淨環境重跑**：至少模擬新使用者照說明執行；記錄警告、耗時與不可避免的差異。
7. **連結結果與版本**：報告或圖表記錄產生它的程式版本、資料版本與參數。

最低重現說明可包含：

```text
研究輸入與取得方式：
不可公開資料的申請或替代測試資料：
環境建立方式：
執行命令與順序：
預期產物與檢查值：
隨機性、硬體或外部服務造成的已知差異：
```

## 工具配方

### 網頁 AI：解釋概念與草擬檢查表

可以根據匿名化的技術棧請 AI 提醒常見重現風險，但不要貼入私有 repo、金鑰或敏感資料。任何安裝命令都應以專案文件與官方來源核對。

### NotebookLM：查詢既有方法與實驗文件

把方法規範、資料說明與實驗紀錄作為限定來源，整理重現前置條件。它不會替你保存本機環境或 Git 歷史，關鍵步驟仍需寫回專案。

### 檔案型 Agent：受控修改研究專案

```text
先檢查目前修改狀態並只回報，不要清除任何既有變更。
列出預計修改檔案與驗證命令，等我確認後再動手。
完成後摘要差異、實際執行的檢查與未驗證項目；不要自行 push 或發布。
```

### Git 與 CLI：建立可比較的證據

使用 `status` 確認範圍、`diff` 審查內容、歷史記錄理解決策，再執行專案既有測試或重現命令。不要用破壞性回復命令處理不屬於本次任務的修改。

## 人工檢查點

- commit 是否混入資料、憑證、個資或不相關格式變動。
- 依賴鎖定是否足以建立環境，而非只寫「安裝最新版」。
- 資料前處理、排除規則與手動修正是否有記錄。
- 固定隨機種子是否只提高可重跑性，而非掩蓋結果變異。
- README 的命令是否由乾淨起點實際走過。

## 常見失敗

- **把 Git 當雲端硬碟**：只有檔案，沒有可理解的修改單位與執行說明。
- **追蹤結果卻不追蹤生成方式**：圖在，但找不到程式、參數與資料版本。
- **只記套件名稱**：版本、系統函式庫與硬體差異仍可能改變結果。
- **AI 自行整理工作區**：可能覆蓋或刪除使用者尚未保存的工作。
- **宣稱完全重現**：若依賴不可得資料或外部服務，應說明可重現的實際邊界。

## 驗收清單

- [ ] Git 只追蹤適合公開或共享的檔案。
- [ ] 每個 commit 聚焦單一目的，訊息能說明研究改動。
- [ ] 資料來源、版本與不可公開條件已有紀錄。
- [ ] 環境與依賴有可執行的建立方式。
- [ ] 核心流程從乾淨起點重跑過。
- [ ] 預期產物與最低檢查值已寫明。
- [ ] 結果能連回程式、設定、資料與參數版本。

## 延伸挑戰

請同儕只根據你的重現說明在另一個目錄執行流程。不要即時口頭提示；記錄所有卡點，再把真正必要的資訊補回專案，而不是只修正你自己的電腦環境。
