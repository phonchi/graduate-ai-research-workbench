## 從願望到規格：看一次前後差異

**願望版**

> 幫我整理這批論文，做得完整一點。

這句話缺少讀者、資料範圍、輸出形式與完成條件。任何工具都只能自行猜測，而猜得愈多，返工機率愈高。

**規格版**

```text
目標：為下週組會整理 domain shift 方法的差異。
背景：讀者了解機器學習，但沒有讀過這批論文。
範圍：只使用 papers/index.md 中標記 A、B、C 的三篇來源。
限制：不新增外部文獻；不把摘要中的數字當成已核對結果。
格式：一頁比較表，加上三個仍待確認的問題。
範例：術語沿用 glossary.md；表格欄位使用「假設／資料／限制」。
驗收：每個比較項都能回到原文位置；無法確認處標記「待核」。

動工前先處理會改變範圍或結論的歧義；
能從現有檔案查到的資訊請先自行查找。
```

規格不必很長。本站建議先寫清三件事：**目標與讀者、材料與動作邊界、交付物與驗收方式**。這已足以讓多數小任務開始。

限制、格式範例與參考慣例則按影響補上：選錯會改變研究主張、公開範圍或產出格式時就先寫；只是低風險細節時，可讓工具採合理預設並回報。上面的規格版把這些資訊全部展開，是完整交接的例子，不是每次都必須填滿的固定表格。

## 反問決策樹

收到任務後，不是「一律先問」或「一律自己決定」。依序判斷：

```text
缺少的資訊能從已授權檔案或既有規則查到嗎？
├─ 能 → 先查，不把檔案探索丟回使用者。
└─ 不能
   └─ 這個選擇會改變資料範圍、研究主張、公開程度或交付格式嗎？
      ├─ 會 → 先反問，附少量互斥選項與建議。
      └─ 不會
         └─ 動作是否不可逆、昂貴或涉及敏感資料？
            ├─ 是 → 停下確認授權。
            └─ 否 → 採合理預設，開始前明說預設。
```

好的問題要讓人容易決定。例如不要問「你想怎麼做？」；改問：「比較表是給 PI 快速決策，還是給口試委員查來源？前者會壓縮成結論，後者會保留原文位置。我建議本次選後者。」

## `AskUserQuestion` 是產品功能，不是通用術語

Claude Code 將多選式澄清工具命名為 `AskUserQuestion`。其他 Chat 或 Agent 可能有不同介面，甚至沒有同名功能。通用能力是：**在高影響歧義尚未解決時取得人的答案**。

沒有專用功能時，直接把行為寫進任務：

```text
若仍有無法從現有資料確認、且會實質改變成果的條件，
動工前最多問我 3 題。能列選項時請給 2 至 3 個互斥選項，
標出你的建議與會造成的差異。低影響細節採合理預設並回報。
```

反問不是逃避判斷。工具能讀取專案時，應先找現有慣例、範例與測試；只有找不到且選錯會造成實質影響時，才把決定交回人。

## 驗收標準要能觀察

避免「專業、完整、好看、正確」這類只能憑感覺判斷的字眼，改成可觀察條件：

| 模糊要求 | 可驗收寫法 |
|---|---|
| 引用要正確 | 每項主張附原始來源位置；抽查三項能回到原文 |
| 不要亂改 | 只允許修改指定路徑；完成後列出實際 diff |
| 程式要能用 | 執行既有測試，回報命令、exit status 與失敗項 |
| 簡報要清楚 | 以實際輸出檢查截字、圖例、字級與數字一致性 |

不要要求模型交出完整內部推理過程。需要可追蹤性時，要求它提供**簡短決策摘要、引用來源、實際命令與可驗證中間產物**。

## 收工前先看最小主線

- 讀者與使用目的是否清楚，資料與檔案範圍是否可定位？
- 哪些動作需要先取得同意，哪些低風險細節可以採合理預設？
- 完成後能否靠來源、diff、測試或實際輸出驗收？

較正式的交接可再按需檢查格式範例是否真的代表慣例、參考資料是否為權威來源。需要一份可直接填寫的版本時，可從[六要素交辦單](/graduate-ai-research-workbench/templates/six-part-brief/)開始刪減，不必為了填滿欄位增加無關資訊。

規格的目的不是控制每一步，而是讓 Agent 在清楚邊界內自行處理低風險細節，把真正需要人判斷的問題留給人。
