## 為什麼需要

重複貼同一串 prompt 容易漏步驟，但太早自動化也會把模糊與錯誤固定下來。三種能力解決不同問題：Skill 保存「怎麼做」的流程；MCP 讓 agent 透過受控介面連接外部資料或工具；subagent 把搜尋、比較或獨立審查拆到不同 Context。

它們都不會自動帶來正確性。研究者仍需決定觸發條件、權限、資料邊界、整合方式與人工核准點。先讓流程人工跑順，再封裝最容易重複且能驗收的部分。

## 任務

選一個至少已做過兩次的研究流程，例如文獻證據表更新、圖表發布前檢查或方法章一致性審查。完成三份設計：

1. **Skill 草稿**：何時觸發、需要什麼輸入、逐步工作流、常見失敗與最低驗收。
2. **MCP 評估**：是否真的需要外部連接；若需要，列出資料、操作、最小權限、測試資料與撤銷方式。
3. **subagent 分工**：哪些子任務能獨立進行、各自的自我完備規格、主 agent 如何整合與解決衝突。

至少選擇一項實作；不需要同時使用三種能力。

## 做法

先畫出目前人工流程，標記輸入、決策、工具、產物與人工檢查點。只有穩定、重複且可驗收的步驟才值得封裝。

**Skill 設計**應包含：

```text
觸發：什麼任務出現時使用？哪些相似任務不使用？
輸入：必要檔案、規格與權限。
流程：可執行的步驟與分支。
失敗：缺資料、工具失效或驗證不通過時如何回報。
驗收：最低可觀察標準。
安全：禁止操作與人工核准點。
```

**MCP 評估**先問四件事：能否用現有檔案或手動匯出解決？介面來源與維護狀態是否可信？需要哪些最小讀寫權限？如何在低風險測試資料上驗證與撤銷？金鑰、cookie 與 token 不得寫入版本控制。

**subagent delegation**只拆可獨立的子任務。每份內部規格要自我完備，寫清背景、目標、範圍、輸入、禁止事項與輸出格式。主 agent 負責去重、處理矛盾、補足跨任務脈絡並對最終答案負責。

## 工具配方

### 網頁 AI：先回顧摩擦與候選流程

```text
請回顧這份人工流程，找出重複、容易漏掉且可客觀驗收的步驟。
不要直接提出複雜自動化；先分成適合保留人工、適合寫成工作手冊、需要外部工具、適合獨立分工四類。
```

### NotebookLM：作為有界來源查詢層

若流程核心是查詢固定來源集，可先用 notebook 驗證問題與引用格式是否穩定。它可作為工作流程的一環，但不應被假設成所有 agent 都能透過 MCP 連接；整合方式需依當下實際支援與官方文件確認。

### 檔案型 Agent：草擬並測試 Skill

讓 agent 先根據一次成功任務與一次失敗案例產生草稿。用代表性任務測試觸發是否精準、步驟是否可執行、失敗是否會停止；通過前不要安裝到廣泛環境。

### MCP：以最小權限接外部能力

先使用唯讀、測試帳號或測試資料。檢查工具能否正確回報權限不足、拒絕破壞性操作並保留操作紀錄。任何 server、client 與 transport 的設定都應以目前官方文件和組織政策核對。

### Subagent：平行搜尋與獨立審查

適合多份材料各自檢查、兩個不共享推理的審查視角，或大範圍搜尋。若工作有共享可變狀態或明確順序依賴，應由主流程逐步執行，不要強行平行。

## 人工檢查點

- Skill 的觸發描述是否會誤套到不相干任務。
- 自動化是否保存來源、版本與操作紀錄，而非只輸出結論。
- MCP 是否取得超過任務需要的資料或寫入權限。
- subagent 是否獨立作業，卻因背景不足產生不可比較的答案。
- 主 agent 是否真的核對分工結果，而非把多份輸出直接拼接。

## 常見失敗

- **第一次做就封裝**：流程尚未理解，錯誤會被制度化。
- **Skill 只有抽象口號**：沒有輸入、分支、失敗回報與驗收。
- **把所有整合都叫 MCP**：先確認實際介面、支援狀態與必要性。
- **給外部工具過大權限**：測試也使用正式資料與高權限帳號。
- **subagent prompt 只寫「照前面做」**：獨立 Context 無法取得隱含背景。
- **平行處理相依任務**：產生衝突版本與重複工作。

## 驗收清單

- [ ] 被封裝的流程已人工成功執行至少兩次。
- [ ] 已說明為何選 Skill、MCP、subagent 或維持人工。
- [ ] Skill 有清楚觸發、輸入、流程、失敗與最低驗收。
- [ ] MCP 僅使用最小必要權限與低風險測試資料。
- [ ] subagent 任務彼此獨立且規格自我完備。
- [ ] 所有自動化都保留人工核准點與可追溯紀錄。
- [ ] 主流程能處理衝突、部分失敗與未驗證結果。

## 延伸挑戰

為同一流程設計「純人工檢查表」與「半自動 Skill」兩版。用三個案例測試時間、漏項與錯誤恢復成本；只有在半自動版明顯改善且不降低可追溯性時，才考慮加入外部工具或平行分工。
