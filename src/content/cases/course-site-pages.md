## 研究痛點

研究程式、資料說明、方法文件與互動成果散落在不同位置時，合作者很難判斷哪一版能重現。直接請 Agent 大改公開站也可能誤刪連結或把未公開結果推上線，因此需要可回復的修改與部署流程。既有課程站在這裡是具體的發布案例，方法可轉用到研究軟體與資料專案。

## 授權輸入

只讓 Agent 讀取已授權的網站原始碼、公開教材、導覽結構與部署設定。含個資的名單、成績、登入憑證、私有 issue、未公開試題與課程平台匯出檔不得進入公開儲存庫。

## 任務規格

每次變更需指定頁面、允許修改的檔案、不可改動項目與驗收網址。合併前至少檢查建置、站內連結、行動版排版與無障礙基本項；部署後再由公開網址確認版本已更新。

## 做法

1. 在修改前建立 Git 存檔點並查看工作樹狀態。
2. 讓 Agent 先讀網站結構與現有慣例，再做範圍明確的小修改。
3. 本地執行建置與連結檢查，檢視差異後才提交。
4. 由 Pages 自動部署，最後用公開網址抽查首頁、導覽與受影響頁面。

## 人工檢查點

研究者要確認發布範圍、版本、限制與成果狀態；也要檢查差異中是否出現敏感檔、絕對路徑、測試帳號或未授權素材。部署成功訊息不等於研究說明與下載檔正確。

## 成果與證據

[資料結構課程講義索引](https://phonchi.github.io/nsysu-math208/lectures/)提供可公開存取的成品，示範多類成果如何集中發布。轉用到研究專案時，完整證據鏈應包括 Git 差異與提交、建置結果、Pages 部署紀錄，以及公開網址中的版本、方法與下載檔抽查。

## 常見失敗

- 本地路徑正常，Pages 的子路徑卻造成圖片或連結 404。
- 只看部署為綠色，沒有打開公開網址驗證。
- Agent 同時重排大量檔案，使真正修改難以審查。
- 把密鑰、名單或未發布試題誤加入版本控制。

## 隱私與授權

公開儲存庫採最小揭露原則，部署前搜尋姓名、信箱、識別碼、token 與私有網址。第三方圖片、字型、程式庫和資料均應保留授權資訊；本案例收錄原作者授權的 lectures 頁截圖，但不複製課程首頁的人員資料。

## 延伸挑戰

加入 pull request 預覽、失效連結排程檢查與 Lighthouse 門檻，並建立內容發布清單，使另一位研究團隊成員能在不熟悉網站框架的情況下完成安全更新。
